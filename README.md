# CasesBot

Бот-сборщик кейс-презентаций для отдела продаж (VK Teams + PHP-монолит).
Полное описание задачи, требований и архитектуры — в [`ТЗ_бот-сборщик кейс-презентаций v1.1.md`](./ТЗ_бот-сборщик%20кейс-презентаций%20v1.1.md).

## Индексация каталога

`php bin/index.php` (и кнопка переиндексации в вебе, и sync-шаг Google Drive — один и тот же
`Reindexer`) обходит `presentations/` и индексирует **все слайды каждой презентации**:
текст, картинки (превью для веб-интерфейса) и комментарии рецензентов
(`python/slide_text_extractor.py`; старый, современный и inline-форматы комментариев) —
комментарии хранятся в базе для контекста разметки, наружу не отдаются.

Слайд по умолчанию считается кейсом; служебные слайды (обложка, о компании, контакты)
эксперт помечает **«не кейс» в веб-интерфейсе разметки** (`public/tags.php`). Метка `#кейс#`
в заметках докладчика осталась нужна один раз — при первом индексе презентации, размеченной
по старому процессу: слайды без метки тогда получают «не кейс» автоматически.

Теги живут в базе, а не в файле:

- **notes** — хэштеги из заметок докладчика (`#erp #ритейл#`) переносятся в каталог при
  индексации, пока слайд не размечен экспертом (`tags_reviewed = 0`);
- **expert** — теги, подтверждённые экспертом в веб-интерфейсе; переиндексация их не
  трогает никогда;
- **предложения** (словарь `config/tags.php` и LLM `LlmTagSuggester`) — не теги, а очередь
  `tag_suggestions`: эксперт принимает/отклоняет каждый в веб-интерфейсе, отклонённое
  не предлагается повторно. LLM получает канонический список тегов и комментарии рецензентов
  как контекст (провайдер и модель — в `.env`: `AI_PROVIDER`, `OLLAMA_*`/`OPENCODEZEN_*`).

Переиндексация не стирает ручное: слайды сопоставляются со строками каталога по содержимому
(`SlideMatcher` — content_hash, затем заголовок, затем похожесть текста), поэтому переживают
перестановка слайдов в Google Slides и правки текста; исчезнувшие слайды и файлы вычищаются.
Вся операция атомарна (одна транзакция SQLite, WAL-режим) — при сбое каталог откатывается
к прежнему состоянию и бот не видит пустую базу; параллельный запуск исключается flock-локом
(Reindexer). Полный текст — в `cases.content`, картинки — файлами в `storage/catalog/images/`
со ссылками в `case_images`. Теги плоские, без категорий (§6.2 ТЗ изначально предполагал
industry/product/technology/client — от категорий отказались в пользу простых тегов).

## Синхронизация с Google Drive (раз в неделю)

`bin/sync.php` + недельный цикл в `docker/entrypoint.sh` (`SYNC_INTERVAL_SECONDS`, по умолчанию
604800 = 7 дней; первый прогон — сразу при старте контейнера). Источник — презентации из
`GOOGLE_PRESENTATION_ID` (можно несколько, через запятую), доступ — сервисный аккаунт Google
(`GOOGLE_SERVICE_ACCOUNT_JSON`, ключ в `config/google/`, папка/файл расшарены на его email).

Алгоритм идемпотентен: сверяет `modifiedTime`/`md5` файла в Drive с состоянием последней
синхронизации (`storage/catalog/drive-sync.json` — папка примонтирована, переживает рестарт
контейнера). Ничего не изменилось — ничего не делает; изменилось — скачивает pptx (нативный
Google Slides — через экспорт `.../export/pptx`, загруженный .pptx — как есть) в
`presentations/` под именем из Drive, запускает переиндексацию каталога (тот же
`Reindexer`, что в веб-загрузчике) и пересобирает публичные копии. Эксперт меняет
презентацию в Google Slides — раз в неделю она сама приезжает на сервер, каталог и
«парадные» копии обновляются без его участия. Ручной запуск: `php bin/sync.php`, флаги
`--skip-reindex` и `--force`.

## Веб-интерфейс: загрузка и разметка (:8081)

Две страницы рядом, обе под HTTP Basic Auth (`UPLOAD_USERNAME`/`UPLOAD_PASSWORD` в `.env`) —
без обоих значений страница отказывает в доступе (fail closed), а не открывается всем без пароля.

- **`public/upload.php`** — загрузить `.pptx` (то же имя файла = новая версия существующей
  презентации, перезаписывает старую) и кнопкой запустить переиндексацию; отчёт показывает
  по каждому слайду статус (новый / переставлен / обновлён / без изменений) и число новых
  предложений тегов.
- **`public/tags.php`** — интерфейс разметки: список карточек по слайдам; слева содержимое
  слайда (превью, заголовок, текст, комментарии рецензентов), справа — утверждённые теги,
  предложенные (принять/отклонить каждый, «принять все») и добавление новых с автодополнением
  по справочнику (с предупреждением о похожем существующем теге — так не плодятся дубли вида
  «авто»/«автопром»). Здесь же — инверсная метка «это НЕ кейс». Вкладка «Справочник тегов»:
  частоты тегов (покрытие кейсами), переименование и слияние дублей одним действием.

Переиндексация из веба заодно пересобирает публичные копии (PublicCopyBuilder — см.
«Сборка презентации»); удаление презентации снимает и её публичную копию.

## Сборка презентации

`SlideCloner` (`python/slide_cloner.py`) копирует слайды между презентациями на уровне сырых частей
OOXML-пакета (python-pptx opc/package API, не через объектную модель) — слайд, его layout, master,
theme и все media копируются как есть, с ремаппингом id/media/layout-master. Внутренние пометки
не копируются вообще: заметки докладчика и комментарии рецензентов (в т.ч. перенесённые в pptx
экспортом Google Slides, старый и современный формат) отсекаются на уровне связей пакета /
отдельных элементов XML — структура и форматирование слайдов от этого не меняются. Проверено:
форматирование (кастомные шрифты, цвета, размеры) сохраняется побайтово идентично оригиналу.

Важно: экспорт Google Slides → pptx может содержать части packа с разными блобами под одним
именем (дубли выдавал старый выбор имён в SlideCloner — исправлено, имена частей раздаются
через реестр занятых на всю сборку, `next_available_partname`).

`PresentationBuilder` вызывает `SlideCloner` для нужных слайдов, затем сам добавляет титульный слайд
(тема + дата) и сохраняет финальный файл в `storage/output/`.

`CaseDeckBuilder` — другой сценарий сборки, для команды `кейсы`: в подборку попадают все слайды,
помеченные «не кейс» в каталоге (обложка, о компании, контакты), плюс найденные по запросу
кейсы — состав определяется базой, а не заметками исходника. Слайды остаются в исходном порядке
презентации — подборка читается как урезанная версия оригинала. Титульный слайд не добавляется.
PDF как формат вывода не используется — LibreOffice headless на Alpine/musl (текущий базовый
образ) падает на старте (баг совместимости, проверено на сервере), поэтому отправляется pptx.

### Публичные копии без пометок (PublicCopyBuilder)

Бот, кроме вложения-подборки, присылает ссылку на оригинал презентации целиком. Даже когда
заметки больше не используются для разметки, pptx из экспорта Google Slides может содержать
комментарии рецензентов — их не должен видеть клиент, поэтому по HTTP на :8080
(docker/entrypoint.sh) отдаётся каталог `presentations-public/`: «парадные» копии без
заметок/комментариев — все слайды исходника в исходном порядке через
`SlideCloner::cloneAll()`. Пересобираются после переиндексации (`public/upload.php`),
из sync-шага Google Drive и вручную (`bin/build-public.php`).

Имя копии можно переопределить независимо от имени исходника:
`config['presentations']['public_name_overrides']` (исходник на Drive -> имя в чате), например
копия «Кейсы направления Бизнес автоматизации.pptx» отдаётся как «Экспертиза направления
Бизнес автоматизации.pptx». При каждой пересборке из папки удаляется всё, что не является
актуальной копией (старые версии, прежние имена, копии удалённых исходников) — в
`presentations-public/` остаётся ровно актуальный набор. Сырые исходники остаются только
для индексации.

Проверка `CaseDeckBuilder` без чат-интеграции:
```
php bin/deck-test.php "Экспертиза направления бизнес автоматизации.pptx" "7,9"
```

## Команды бота

Команды — отдельные классы в `src/Bot/Commands/`, реализующие `CommandInterface` (`matches()` +
`handle()`); `ChatBotController` перебирает их и передаёт управление первой подошедшей. Добавить
новую команду — значит просто добавить новый файл в эту папку и зарегистрировать его в `bin/poll.php`.

**`кейсы`** (`CasesCommand`) — ищет и ранжирует кейсы по тегам (`CatalogRepository::findByTags`,
больше совпадений — выше, лимит `MAX_SLIDES_PER_DECK`, §5.1.3 ТЗ). Теги — простые слова через
запятую/пробел (без категорий), с резервом на синонимы (`TagTaxonomy`, `config/tags.php`) —
свободный текст всей фразы целиком (`QueryParser`) ещё не реализован:
```
кейсы ритейл
кейсы производство, 1с
```

**Минимум кейсов в подборке** (`MIN_SLIDES_PER_DECK`, по умолчанию 5): если по тегам нашлось
меньше, подборка добирается «похожими» кейсами — сначала по связанным тегам
(`TagTaxonomy::relatedTags`, карта `config/tag-relations.php`), затем — по смыслу через LLM;
добранные кейсы помечаются в сообщении отдельно. Присылать клиенту подборку из одного кейса —
хуже, чем дополнить её близкими по теме. Если каталог и после добора короче минимума — присылается
то, что нашлось.

По каждой затронутой исходной презентации собирает и отправляет pptx-подборку (`CaseDeckBuilder`,
см. «Сборка презентации»), а следом — в любом случае — ссылку на оригинал презентации
целиком и номера слайдов, которые нужно оставить, если подборку нужно поправить вручную. Если
сборка не удалась (или `CaseDeckBuilder` не настроен) — присылается только ссылка.

Если ничего не найдено — бот присылает список реально используемых в каталоге тегов вместо пустого
файла (§5.1.7 ТЗ).

Если же ни одно слово запроса вообще не совпало ни с одним известным тегом (ни в `TagTaxonomy`, ни
в базе), а LLM-провайдер настроен (`.env`: `AI_PROVIDER`, `OLLAMA_*`/`OPENCODEZEN_*`), команда не
сдаётся сразу с подсказкой по тегам, а отдаёт запрос целиком и текст всех видимых кейсов каталога
(`CatalogRepository::allForMatching` — текст уже лежит в `cases.content` с момента индексации,
повторно читать презентации не нужно) в `LlmCaseMatcher`. Модель либо возвращает id кейсов,
подходящих по смыслу (отрасль/продукт/технология/клиент), либо явно отвечает, что подходящих нет —
тогда бот показывает тот же список доступных тегов, что и при обычном пустом результате. Без
настроенного провайдера поведение прежнее — подсказка с примерами синтаксиса.

Проверка без чат-интеграции — то же самое, что делает команда, но из консоли:
```
php bin/build-test.php "производство, 1с"
```

## Этапы разработки (§9 ТЗ)

1. **Недели 1–2** — `Indexer`, `CatalogRepository`, `TagTaxonomy`: построение каталога, проверка тегирования/поиска через `bin/index.php`. ✅
2. **Недели 3–4** — `SlideCloner`, `PresentationBuilder`: сборка pptx (готово, проверено на форматировании) ✅; команда `кейсы` в VK Teams ✅ — но по явным тегам, не свободному тексту (`QueryParser` с синонимами ещё нет).
3. **Неделя 5+** — пилот на реальных запросах, донастройка справочника тегов и лимитов.
4. **Разметка в веб-интерфейсе** — теги и метки «не кейс» живут в базе (`public/tags.php`), LLM предлагает — эксперт решает, минимум кейсов в подборке с добором по связанным тегам и смыслу. ✅
