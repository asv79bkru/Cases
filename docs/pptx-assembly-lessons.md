# Уроки сборки PowerPoint-файлов: почему нельзя пересобирать OOXML-пакет «с нуля»

Дата: 04.11.2026. Контекст: CasesBot — бот собирает pptx-подборки для клиентов (VK Teams)
из презентаций, которые эксперт правит в Google Slides. Часть — заметки/комментарии
рецензентов — должна вычищаться. Источник после правок приходит на сервер как
**экспорт Google Slides → pptx** (не нативный pptx) через Drive API.

## Симптомы (хронология)

| Период | Скрипт сборки | Что видел клиент в PowerPoint |
|---|---|---|
| июль 2026 | python-pptx: новая `Presentation()` + копирование слайдов | Диалог «Восстановить» → после ремонта открывался |
| 04.11.2026 (регресс) | то же + уникальные имена частей | «PowerPoint не может прочитать файл» — вообще никак |

При этом **все программные проверки дек проходил**: `zipfile.testzip()` чисто,
`[Content_Types].xml` консистентен (нет частей без типа, нет Override-ов без части),
все внутренние rels указывают на существующие части, python-pptx открывает и отдаёт
правильное число слайдов, дубли имён частей отсутствуют. **Вывод: программные
валидаторы OOXML не доказывают открываемость в PowerPoint.**

## Расследование (GMEM: как это делается)

1. **COM-оракул** — настоящий PowerPoint на машине разработчика, управляемый из PowerShell.
   Обычный `New-Object -ComObject PowerPoint.Application` ломался
   (`TYPE_E_CANTLOADLIBRARY`, 0x80029C4A — битая библиотека типов Office) — обошли
   **поздним связыванием** через `GetType().InvokeMember(...)` (минуя интероп-сборку).
   Результаты: HRESULT `0x80070570` = «файл повреждён, не прочитан»;
   `0x80CB4404` = файл открыт, но **требует ремонта** (это тот самыйJuly «Восстановить»).
2. **Бисекция-monkeypatch**: три подозреваемых изменения клонера отключались по одному
   (патчинг атрибутов загруженного модуля: `mod.next_available_partname`,
   `mod.is_skipped_rel`, `mod.strip_inline_comments`). Виновник определился за 3 прогона:
   смена способа назначения имён частей превращала «ремонтопригодно» в «не открывается».
3. **Контрольные материалы из Downloads**: старые деки (июль/октябрь/ноябрь —
   «нужен ремонт»), сырой экспорт Google (открывается чисто), наша пересборка
   («повреждён»). Одним прогоном оракула.

## Корневые причины

1. **Пересборка пакета с нуля.** python-pptx-сборка стартует с дефолтного шаблона
   `Presentation()` и копирует части — итоговый пакет PowerPoint считает «нуждающимся в
   ремонте» даже при полном сохранении контента. Причина до байта не выяснена
   (зафиксировано как воспроизводимый факт: python-pptx `save()` того же исходника без
   единого изменения → 0x80070570; сырой файл → открывается).
2. **Коллизии `next_partname`**: во время сборки свежесозданная часть ещё не привязана к
   sldIdLst → недостижима для `iter_parts()` → два РАЗНЫХ исходных блоба получали одно
   имя → в zip два энтри с одинаковым именем, PowerPoint repair выбрасывает «лишний»
   (картинки теряются/ломаются).
3. **Попытка починить г-3 уникальными именами** сделала файл неисправимым (см. п.1-№2 в
   симптомах) — откачено; `next_partname` оставлен, а/cc выбран путь, обходящий
   пересборку вовсе.

## Принятое решение: prune вместо rebuild

`python/slide_cloner.py`, режим `prune`:
- **байт-в-байт копия исходного файла** (`shutil.copyfile`),
- у каждого слайда, не попавшего в keep: снять `p:sldId` из `sldIdLst` + связи
  presentation-части на слайд (`drop_rel`) — слайд и только его media выпадают при save;
- у оставшихся слайдов снять связи notes/comments (`is_skipped_rel`: NOTES_SLIDE +
  любой reltype, содержащий `comment`) + вычистить inline `p:cmLst`;
- снять `commentAuthors` от presentation-части + удалить `p:cmAuthorLst` из XML
  presentation;
- `prs.save()` — детали упаковки остаются исходными.

Результат (проверено COM-оракулом): деки и полные копии из экспорта Google открываются
**без всякого ремонта** (8 и 82 слайда; серверная копия, скачанная по HTTP — тоже).

## Правила на будущее (для любых проектов с OOXML)

1. **Режь исходник, не собирай новый.** Чтобы удалить/выбрать слайды или части — работай
   с копией исходного пакета (удаление связей + элементов), не собирай пакет через
   объектную модель (python-pptx, PHPOffice и т.п.). Пересборка = ремонт/отказ в PowerPoint.
2. **Санацию делай отвязкой связей.** Заметки, комментарии, служебные части — drop_rel
   (+ снять inline-элементы нужного namespace); недостижимые части выпадают при save сами.
3. **Программная валидность ≠ PowerPoint-открываемость.** Обязателен финальный тест
   реальным PowerPoint'ом (COM-оракул; код — в этом документе) или Open XML SDK validator.
4. **Тестируй на том источнике, который реально уедет в прод.** Экспорт Google Slides,
   ручной pptx эксперта и т.п. — пакеты с разными особенностями; фикс на одном источнике
   не переносится на другой автоматически.
5. **Дубли имён частей — тихая потеря данных** (последний энтри побеждает). Ловим по
   `ZipFile.testzip()` + подсчёту дубликатов имён + `UserWarning` от python zipfile.
6. **Регресс-набор**: сырой файл источника («читается»), деки всех режимов сборки;
   артефакты складывать в `storage/output`/temp и прогонять оракулом после КАЖДОГО
   изменения клонера.

## Рецепты

### COM-оракул (PowerPoint из PowerShell, позднее связывание)

Сохранено в `scripts/pp_open.ps1` (рядом с деплоем): принимает `-Path`, открывает
ReadOnly без окна, печатает `ОТКРЫЛСЯ, слайдов: N` либо `ОШИБКА ОТКРЫТИЯ: <HRESULT>`.
Launch: `powershell -ExecutionPolicy Bypass -File scripts\pp_open.ps1 -Path <файл.pptx>.
Перед каждым вызовом: `Get-Process POWERPNT | Stop-Process -Force` (PowerPoint не всегда
отдаёт экземпляр закрытости).

### Бисекция изменений клонера

Загружать модули по путям (`importlib.util.spec_from_file_location`) и патчить атрибуты
модуля; `copy_part_and_deps` ссылается на свои хелперы через глобальные имена модуля —
это делает monkeypatch точным. По одному изменению за прогон + оракул на каждый вариант.
